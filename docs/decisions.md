## D-029 · 2026-08-25 · Economic value = a per-cell volatility-targeting backtest that cannot run a model   [SETTLED]
Decision: `volbench.econ.volatility_target_backtest(rows, ...)` implements docs/research_design.md's economic-value metric: `position_t = min(target_vol / forecast_vol_t, leverage_cap)`, applied to the realized return of `t+1`, net of `cost_bps` on `|position_t - position_{t-1}|` (default **10 bps**, the research design's figure), reporting annualized return, annualized vol, Sharpe net of costs (and gross), maximum drawdown, average leverage, turnover and cost drag. It consumes **stored forecast rows only** — it imports nothing from `volbench`, so it cannot reach a model, a splitter or the evaluator, and `tests/test_econ.py::TestBoundary` asserts that from the module's AST and its bound globals. Conventions, all explicit: `realized_return` is a log return, used as-is for sizing (consistent units with the forecast variance) and converted with `expm1` before levering so the equity curve compounds like capital; annualization is per asset (**252** equities, **365** crypto, `periods_per_year_for`, its crypto list pinned against `CRYPTO_PANEL` by test); the vol target is quoted annualized (10% default) and converted to daily units exactly once, so one target means one risk on either calendar; the risk-free rate defaults to 0 and no borrowing spread on leverage is modelled; an unusable forecast sizes to **zero** rather than being dropped, and `n_flat` counts it.
Why: the alignment is the leakage-critical line, and a wrong answer there does not raise, does not produce NaNs and does not look wrong — it produces a *better* Sharpe. Making the row the alignment (a stored row is already "forecast at origin, realization at origin+h") reduces the whole backtest to one element-wise product, so there is no place for an off-by-one to hide, and the module contains no `shift`/`reindex`/`roll` at all. It is pinned three ways: the arithmetic by hand, a one-row shift of the realized-return column that must move the Sharpe by >25%, and the structural check. The one-cell restriction exists for the same reason: averaging two models' forecasts into one position is a backtest of neither. Refusing to import the evaluator is what makes "computed after the fact from an already-hashed table" a structural fact instead of a promise.
Alternatives rejected: dropping unusable-forecast rows (splices two non-adjacent days into one turnover step and under-charges the cost of getting out); working entirely in log space (cheaper, but the maximum drawdown is then not a drawdown of capital); annualizing everything at 252 (a crypto Sharpe would be understated by sqrt(365/252) ≈ 1.20 against an equity one, and the two are compared in the same table); an uncapped position (as forecast vol → 0 the position → ∞, and the headline number is decided by the three calmest days).
Revisit-if: the paper reports a financed variant (a borrowing spread on `position > 1`); or portfolio-level economic value is wanted, which is a different object — v1's guard rail excludes multivariate work and the aggregation layer over per-asset results is not designed.

## D-028 · 2026-08-25 · Local multiprocessing executor: forkserver by default, kernel family carried into workers, byte-identity is the gate   [SETTLED]
Decision: `volbench.execute.ProcessExecutor` is the second execution backend — `concurrent.futures.ProcessPoolExecutor`, configurable worker count, one pool per `map` call, **`forkserver`** start method by default with `fork` and `spawn` available. The serial backend's behaviour is untouched. Four properties beyond mapping: (1) **byte-identity is a test, not a claim** — `tests/test_runner.py::TestSerialParallelIdentity` runs one grid through both backends into two stores and compares the parquet bytes fragment by fragment, with an inert-proof companion that perturbs one input by one ulp and asserts the comparison notices; measured again at grid scale in docs/P3_RUNNER.md (32 cells, 4/8/16 workers, both start methods, one fingerprint). (2) **The numpy kernel family travels with the work (D-026)**: the parent's `NPY_DISABLE_CPU_FEATURES` is propagated into every worker verbatim, including "unset", and every worker compares its own enabled dispatch targets against the parent's (`kernel_signature()`) and refuses the task if they differ. (3) **Rule 1, no nesting, is enforced** — `map` raises inside a worker instead of deadlocking a bounded pool. (4) **`fork` is refused where it would hang**: in a process that has already imported a fork-unsafe backend (`FORK_UNSAFE_MODULES`, today `lightgbm`), which is an exact test of "already used" because those backends are imported inside `fit` and nowhere else (D-022). `ProcessExecutor` knows nothing about GPUs; that is D-027's job.
Why: D-011's H4 claim is "same forecasts, three execution paths, verified identity", and until this branch the second path did not exist and the identity was unverified. It is checked on the *bytes* rather than on the frames because a difference the dtypes or the row order absorbed would still be a difference in what a later analysis reads off disk. **The start method is `forkserver` because plain `fork` was measured to deadlock**: a parent that has trained a LightGBM model and then forks produces workers that hang on their first LightGBM call — OpenMP's locks are copied in whatever state the parent's threads left them. The same cell completes in 0.19 s with `OMP_NUM_THREADS=1` set before the parent starts and in 1.2 s under `forkserver`, which is the signature of inherited state rather than of load. It is not hypothetical: a script that runs one grid serially and the next through a pool — or a pytest session that does both — hits it exactly, and it is how it was found. `forkserver` is still fork-based (workers are forked from a *clean* server process), costs about a second per pool against grids measured in hours, and was measured at 31.99 s versus `fork`'s 31.62 s on the same 32-cell grid — a 1% difference for a class of failure removed. The kernel-family propagation is D-026 applied one level down: a worker that selected a different family would produce different content digests and therefore different config hashes for the same experiment — a cache miss, not a wrong answer, but a wasted grid and a broken identity claim. Inventing a pin value the parent did not have would be worse than propagating none, because the pool would then disagree with a serial run in the same shell.
Alternatives rejected: `fork` as the default with the hazard only documented (a deadlock is indistinguishable from a slow grid until someone kills it, which is exactly how this cost an afternoon); `spawn` as the default (works, marginally slower, and gives up nothing `forkserver` keeps); setting `OMP_NUM_THREADS=1` at `models/lgbm.py` import to make `fork` safe (fixes the measured case at its source, and the adapter already pins `num_threads=1` for determinism — but it is a global side effect on every OpenMP consumer in the process, including torch and BLAS, from a library import); limiting worker threads for speed — **explicitly rejected on evidence**: the OpenBLAS thread count changes GARCH's numbers (docs/P3_RUNNER.md §6), so a pool that quietly single-threaded its workers would stop reproducing the serial backend, which is the one thing this class must never do; a persistent pool on the executor object (an executor then holds OS resources and cannot sit in a config); threads (the GIL, and no isolation of a model backend's global state); asserting identity on the DataFrames (see above).
Revisit-if: the Slurm-array backend lands (it joins the same parametrized contract tests and the same identity gate); or `FORK_UNSAFE_MODULES` needs to grow, which is a sign the default should simply be enforced rather than defaulted.

## D-027 · 2026-08-25 · Grid runner: resumable by construction, per-cell isolation, declared lanes   [SETTLED]
Decision: `volbench.runner.run_grid(grid, source, store, ...)` orchestrates the full `asset x model-config x horizon x protocol-arm` cross and returns a `RunManifest`. Four properties. (1) **Deterministic ordering**: `GridSpec.cells()` sorts by `(asset, model label, horizon, arm label)`, never set/dict iteration order, so two descriptions of one grid produce one manifest ordering. (2) **Resumable by construction**: a cell whose `config_hash` is in the store is skipped by `run_backtest`'s own short-circuit, before any fit; there is no run state on disk beyond the results, so resuming and extending a grid are the same operation, and a re-run leaves existing fragments byte-identical *and unrewritten* (the tests check mtimes as well as bytes). (3) **Per-cell fault isolation**: a cell that raises is recorded `status="failed"` with the exception type and message, logged at WARNING, and the grid continues; only `Exception` is caught; `n_missing` rides on every outcome so the evaluator's finer-grained per-origin failures stay visible from the manifest. A failure of the *data source* is deliberately NOT isolated and propagates. (4) **Lanes**: `ModelConfig.lane` is `"cpu"` (fan out) or `"gpu"` (serialized, its own executor), **declared in the config, never inferred from a model's name**, and the lanes run CPU-first (`LANE_ORDER`). `AssetData` is loaded once per asset in the parent process before any cell runs. The `horizon` dimension is the splitter's horizon, so a cell at `H` scores every `h <= H` and horizons 1 and 5 are different experiments.
Why: the grid is the last piece the paper's numbers go through and it must survive being interrupted, because it will be. Making the store the only run state is what makes that safe: a manifest is a record, never an input, so there is deliberately no reader for one and a stale manifest cannot corrupt a grid. Per-cell isolation is the evaluator's per-origin philosophy one level up — a model that cannot fit one asset must not cost the other 200 cells — while a wrong data path is a wasted grid rather than a result, which is why that one stops the run. Lane routing is declared because a name-based guess misroutes the first adapter that breaks the pattern and the failure mode is a CUDA OOM halfway through a grid. CPU-first is not cosmetic: the CPU lane forks and forking a process that has already initialized a CUDA context is undefined behaviour.
Alternatives rejected: a `Runner` class (the plan's shape; a function over dataclasses matches `run_backtest` and holds no state); a run-state file or a resumable manifest (two sources of truth about what is done, one of them editable); recording every cell of a missing asset as "failed" (a grid that ran for an hour and reports 200 failures because a path was wrong); inferring the GPU lane from the model name; running the lanes concurrently by default (needs the GPU lane in its own process from the start, and the safety then depends on what a model's `fit` imports); GPU *batching* across assets (the plan's other half — it reintroduces cross-series padding and alignment and needs its own leakage check; still open).
Revisit-if: the Slurm backend lands and the grid is sharded across jobs rather than lanes; or the wall-clock cost of the idle GPU during the CPU lane is measured and turns out to matter (design.md open questions).

## D-031 · 2026-08-25 · PatchTST's device class is hashed; the ordinal is not   [SETTLED]
Decision: `PatchTST.spec()` carries `device_class` — `"cuda"` or `"cpu"`, the torch device *type* — so a CPU fragment and a GPU fragment of one configuration are two cells with two config hashes. The ordinal stays out: `"cuda:0"` and `"cuda:1"` hash identically. `device="auto"` resolves against the machine (and so needs torch importable); an explicit device keeps `spec()` a torch-free call. `tests/test_models_patchtst.py::TestDeviceClass` asserts the two classes cannot share a hash and that the ordinal cannot split one.
Why: with dropout on, each device draws its masks from its own RNG stream, so a CPU fit and a CUDA fit of the same seed are two different training realizations — ~1.6% apart on a 300-point window when the adapter was built, and pinned by `TestGpu::test_with_dropout_cpu_and_gpu_are_different_realisations`. The store is content-addressed: one hash must mean one artefact, so the thing that picks the realization has to be in the hash. Until now it was not, and two numerically different fragments could share one `config_hash` with the store free to serve either for the other. Flagged at the Phase-2 integration (docs/P2_INTEGRATION.md §3.4, §6.6) and left as a protocol call; this is the call. The ordinal is placement, not identity, and excluding it is what lets a multi-GPU grid put a cell on whichever card is free. The zero-shot TSFM adapters are untouched: they estimate nothing, so no RNG stream is drawn from.
Alternatives rejected: pinning the paper's runs to one device class and leaving `device` unhashed (works only as long as nobody runs a CPU cell into the same store — a discipline, not a mechanism); hashing the full device string (a grid could then never move a cell between cards without orphaning it); hashing the GPU model as well (honest but unenforceable across a cluster, and it is the same qualification D-026 already puts on the numpy kernel family: the paper states its hardware); making `device="auto"` fall back to `"cpu"` without torch (a guess about what a machine would have done, recorded as if it were a fact).
Revisit-if: PatchTST's `dropout` is set to 0 for the study, which would make the two classes agree to float rounding and the distinction cosmetic; or a device class beyond cpu/cuda enters the study.

## D-030 · 2026-08-25 · HAR retransforms through `models/_rv`, Duan smearing by default   [SETTLED]
Decision: `HAR` gains `retransform: Retransform = "smearing"` and goes through `volbench.models._rv` like every other log-RV model in the package (D-025). The arm is in `spec()` and in `name` — `har_rv-smearing` / `har_rv-gaussian` — so the two can never collide onto one config hash; `"gaussian"` reproduces the pre-0.5.0 `exp(y_hat + resid_var/2)` exactly and is kept as the like-for-like arm, pinned by test. Both factors are estimated once at the scheduled fit and neither moves under `update`. Every HAR hash and every HAR number moved, and the package version went 0.4.0 → 0.5.0 with them.
Why: D-025 settled one shared retransformation and left HAR as the single hold-out — which was awkward in itself, and worse because HAR is the model the M2 measurement was *taken on*: docs/M2_NOTES.md recorded its Gaussian correction over-inflating to 1.13x the toy fixture's known true close-to-close variance on the D-016 target, because the overnight jump is a near-chi-squared single shock and the Gaussian-log-residual assumption is mis-specified for it. Measured at the switch, on the toy fixture, 200 origins, window 500, refit every origin: **forecast/true 1.1320 → 1.1102**, **QLIKE-against-the-truth 0.0263 → 0.0242**, QLIKE against the scored proxy 0.1823 → 0.1806, the 5% VaR hit rate unchanged at 0.035. The `gaussian` arm reproduces the old numbers to every printed digit, which is what makes the comparison a measurement rather than an assertion. Reported plainly: that is about a sixth of the overshoot removed — an improvement, not a cure. Taken **before** any grid freeze, because a modelling change that moves hashes and numbers after one would invalidate the frozen results.
Alternatives rejected: leaving HAR on the Gaussian arm as "the model the literature describes" (Corsi 2009 does not settle the retransformation, and the package would keep two defaults for one operation); switching the default silently without measuring (the whole point was that the effect is small enough to be assumed wrongly in either direction); waiting for the component overnight+intraday HAR that would address the mis-specification at its source (a bigger modelling change, still open, and not a reason to keep the worse of two available corrections).
Revisit-if: the component overnight+intraday HAR is built, or an out-of-fold factor lands for the high-capacity log-RV models (design.md open questions) — the same estimator question applies to HAR's own in-sample residuals.

## D-019 · 2026-08-25 · Fit window = 500 observations; 1000 is the robustness arm   [SETTLED]
Decision: the rolling-origin fit window for panel runs is **500 observations** (`volbench.data.panel.FIT_WINDOW_DEFAULT`). **1000** stays available as the robustness arm (`FIT_WINDOW_ROBUSTNESS`), not as a deprecated setting. Both are ordinary `RollingOriginSplitter(window=...)` values, so both are already in every `config_hash` through the splitter and the two arms can never collide onto one cached cell; a test pins that rather than leaving it to inspection. docs/PANEL_REPORT.md §8.1 reports the crisis coverage at both.
Why: measured, in the report the panel stream produced. At 1000 the global-financial-crisis window is largely *inside the warm-up*: the panel holds 140–149 GFC days per equity series and the evaluation scored **31–86** of them (SPY and DIA scored 31, losing 79%), while BTC/ETH scored **0** of their 90 COVID days because 1000 days from the 2017 listing runs to 2020-05-13. At 500 the same panel scores **140–149** GFC days per equity series — every series that has GFC days now scores all of them — and **90/90** COVID days on both crypto series. H3 ("TSFM relative performance degrades in crisis sub-samples") is thereby testable on all four settled crisis windows instead of three, and the GFC arm stops being a remnant. The panel *had* those days all along; only the protocol was hiding them.
Alternatives rejected: keeping 1000 and reporting GFC as a partial sub-sample (throws away the crisis the paper most wants to show, for estimation sample the econometric models do not need — HAR is 4 parameters, GARCH(1,1) is 4); a GFC-only ablation at a shorter window (two windows in one results table, and a crisis result produced by a protocol used nowhere else invites exactly the suspicion it should avoid); extending the panel start before 2005 (changes D-004's stated span and only helps the seven series with the history); 750 as a compromise (recovers GFC but not crypto COVID, and no measurement argues for it).
Revisit-if: a model in the grid is measurably window-starved at 500 — the robustness arm exists to detect that, and a ranking that flips between 500 and 1000 is a finding, not a bug. Note the two arms cost two grid runs; if compute forces a choice, the robustness arm is the one that shrinks (fewer models or fewer assets), never the crisis coverage.

## D-018 · 2026-08-25 · Invalid-target policy: unusable days leave the fit window, never the results table   [SETTLED]
Decision: an **invalid target day** is a day whose primary variance target is NaN **or ≤ 0**. Both roles such a day plays are settled, and differently:
(a) **Scoring** — it keeps its place on the calendar. The row is produced, the scores are NaN, and `missing_reason` names the cause. A zero is routed there explicitly (`proxy_nonpositive`) rather than arriving as a crash: QLIKE is `v/y − log(v/y) − 1`, undefined at `y = 0`.
(b) **Fitting** — it is dropped. The variance series handed to any model is **compacted**: for a window of `N` positions ending at origin `t`, the model receives the last `N` **valid** observations at positions `≤ t`. Where invalid days sit inside the span the window's calendar extent stretches further into the past; its last observation never moves past the origin.
Implemented at the **series-loading layer** — `volbench.compaction.FitSeries`, handed out by `PanelSeries.fit_input()` — so every adapter is covered by one implementation and none sanitizes its own input. The splitter still runs on the full calendar: origins and targets stay calendar positions, and compaction happens when a window is materialized. The policy name enters the config hash (`protocol.invalid_target_policy`) whenever it is not `"none"`, so the compacted and uncompacted arms cannot share a cache entry. An origin with fewer than `N` valid observations behind it — possible only at a series' start — raises `InsufficientHistoryError`, which the evaluator turns into the standard NaN-plus-`missing_reason` row: a short window is never silently fitted, because the run would then report a window length it did not use.
Why: 125 days of the panel are invalid, from three mechanisms: 109 from bars whose close printed outside their own session range, so the range targets are NaN (TWSE 80, CAC 28, HSI 1); 14 where a monotone bar met a stale open, making Rogers-Satchell and the overnight term both exactly zero (HSI 12, NKX 2); and 2 first-in-window days with no previous close for the overnight term (SPY and DIA, both 2005-02-25) — structural rather than a defect. Every log-RV model takes `log(RV)`, so before this a *single* unusable day failed every training window containing it. Measured on the real archives at window 500, `refit_every=21`: uncompacted, HAR produces a forecast at **63.5%** of HSI's 4828 origins and **48.4%** of TWSE's 4801; compacted, at **100%** of both, with exactly 13 and 80 rows flagged — the days whose own target is unmeasurable, and no others. Half a model's column was disappearing into correctly-recorded NaN rows on a data defect nobody had decided to accept.
Alternatives rejected: (a) let the models fail and report the NaN rows (what the code did; the measurement above is what it costs); (b) floor the target at a small positive value (changes the estimator and invents a variance nobody measured — and the floor's value would silently set the model's worst-case loss); (c) drop HSI and TWSE (two venues lost to a source-file artefact); (d) impute the missing variance from neighbours (a forecast target built from data the day did not produce, and on the overnight-plus-range estimator the neighbours are exactly what is being forecast); (e) compact by taking the valid subset of the splitter's own window (the effective sample then varies by origin and by series, so "window = 500" stops describing what any model was fitted on); (f) drop the day from the panel outright (it would vanish from the results instead of being recorded as unscorable, which is the one thing this project's results contract has never allowed).
Revisit-if: (1) **Lag semantics.** For models reading *positional* lags of the fit series — HAR's daily/weekly/monthly components, LightGBM's 22 lags — "yesterday" now means the previous *measured* day, so a lag can span two or more calendar days on the six affected series. Documented in both adapters and in docs/design.md; whether the paper reports HAR's memory in calendar days or in observations is still open. (2) If a future series carries invalid days in *blocks* rather than singly, a window could stretch materially in calendar time, and the honest response is to report the stretch, not to hide it — `FitSeries.dropped_positions` exists for exactly that.

## D-026 · 2026-08-25 · Byte-identity is claimed within one numpy SIMD kernel family; CI and `reproduce` pin x86-v3   [SETTLED]
Decision: `make reproduce` and CI export `NPY_DISABLE_CPU_FEATURES="X86_V4 AVX512_ICL AVX512_SPR"`, so every machine computes the toy benchmark's proxies with numpy's x86-v3-or-lower `log`/`exp` kernels — the family the committed identities were computed with. The determinism rule (CLAUDE.md 3) is restated as: same seed, same code, same data, **same kernel family** ⇒ byte-identical results and hashes. The paper's grid runs on one kernel family and says which.
Why: found by CI at the Phase-2 integration (docs/P2_INTEGRATION.md §3.6). The pinned-identity test failed on some GitHub runners and passed on others for the same commit; the only difference was the content digest of the overnight-plus-range proxy, i.e. the last bit of `np.log` on an AVX-512 runner. Content digests of computed series are the cache-identity control and cannot be dropped; a mismatch across families causes a false cache *miss*, never a false hit, so correctness is unaffected — only the byte-identity claim needed qualifying. Disabling a feature the machine lacks is a silent no-op in numpy, so the pin is safe everywhere.
Alternatives rejected: hashing the raw fixture bytes instead of the computed arrays (weakens the leakage control that a revised or longer series can never be served for this one); a correctly-rounded `log` (none in numpy); tolerating the failure as flaky (it is a real, explained difference).
Revisit-if: numpy makes its SIMD transcendental kernels bit-identical across dispatch targets, or the grid moves to a machine class where the v3 kernels are unavailable.

## D-025 · 2026-08-25 · One log-to-variance retransformation, shared (`models/_rv.py`)   [SETTLED]
Decision: every model that fits `log RV` and must return a *variance* (a mean, not a median) retransforms through `volbench.models._rv` — Duan (1983) smearing `exp(mu) * mean(exp(e_i))` over the fit window's in-sample residuals as the DEFAULT (`retransform="smearing"`), the Gaussian `exp(mu + sigma^2/2)` kept as the like-for-like arm against HAR. AutoETS, AutoARIMA, LightGBM and (since the integration) PatchTST use it; the choice is in `spec()` and in the model `name`, so the two arms can never collide onto one config hash. The factor is estimated once at the scheduled fit and never re-estimated by `update`.
Why: three streams would otherwise have carried three copies of the same four lines (the tsfm stream flagged its own). docs/M2_NOTES.md measured the Gaussian correction over-inflating HAR's forecast (1.13x the fixture's known true variance) on the noisy overnight-plus-range target; smearing reads the correction off the residuals instead of assuming their shape.
Alternatives rejected: Gaussian default (the M2 measurement); no correction (a median forecast scored as a variance — a systematic downward bias).

## D-017 · 2026-08-24 · The scoring target is a property of the evaluation cell, never of the model   [SETTLED]
Decision: one scoring target per run, shared by every model in it. `ModelEntry.target` — a short-lived per-model field — is removed; the benchmark takes a single `target` argument (`"overnight_plus_range"` by default, D-016's close-to-close estimator; `"parkinson"` as a *labeled* robustness arm, never a silent default) and every cell in the run is scored against it. What a model is *fed* stays a modelling contract and does not move with the flag: a variance-fed model's fit input is always the close-to-close series, whatever the run is scored against. The target reaches the config hash through `proxy_name` and the proxy's content digest, so two targets can never share a cell. Implemented at the M2 cleanup; `tests/test_toy_targets.py` pins it, including that no model object carries a `target` attribute at all.
Why: with per-model targets the QLIKE column compared models against *different* proxies, which is not a comparison — a model scored against Parkinson and a model scored against overnight-plus-range differ by the overnight variance (33–51% of close-to-close variance on the real panel, docs/PANEL_REPORT.md §6), which swamps any difference between the models. Forecasts do not depend on the proxy, so a shared target costs nothing: switching it re-scores the *same* forecasts, moving QLIKE and the proxy columns and nothing else, which is what makes proxy-robustness of the rankings (Patton 2011) checkable at all.
Alternatives rejected: per-model targets with a warning in the table caption (the numbers still get compared); scoring every model against every target in one frame (a results table with a target dimension nothing in the analysis needs, and a config hash that stops identifying one cell).
Revisit-if: n/a for the rule. The open question it neighbours is D-016's second revisit item — the return-fed models are scored against the close-to-close proxy while forecasting close-to-close variance, which is now consistent by construction; a model family that genuinely forecasts a *different* quantity would need its own cell, not its own target.

## D-016 · 2026-08-24 · HAR scoring target = per-day overnight + Rogers-Satchell   [SETTLED]
Decision: HAR-RV is fed and scored against a per-day CLOSE-TO-CLOSE variance estimator, `overnight_plus_range_variance` = `(ln(O_t/C_{t-1}))^2 + RS_t` with `RS_t` the Rogers & Satchell (1991) drift-independent range term — not plain Parkinson, and not literal Yang-Zhang.
Why: HAR forecasts the variance of the next close-to-close return, so it must be scored against an estimate of that quantity. A range proxy (Parkinson/Garman-Klass/RS alone) estimates only the intraday open-to-close variance and structurally omits the overnight jump (~9% of return variance in the toy fixture, more on real indices), biasing the scored forecast low (M1 report §4.4). Validated against the toy generator's known true variance: the new target's bias is ~a quarter of Parkinson's and its sampling variance ~7x below the squared return's (`tests/test_target_estimators.py`). RS is used, not Parkinson, for the intraday piece because it stays unbiased under drift; formulas corroborated 2026-08-24 across CRAN TTR, arXiv:1803.07152 and portfoliooptimizer.io (primary papers paywalled).
Alternatives rejected: (a) Yang-Zhang — a windowed multi-day estimator; per-day it is undefined, and a window reaching past day t would put the future into day t's target (look-ahead). (b) squared daily return — unbiased but ~7x noisier. (c) leaving HAR on Parkinson — the M1 mismatch.
Revisit-if: two open consequences, both in docs/M2_NOTES.md. (1) HAR's lognormal retransformation is sensitive to the target's log-space noise — on the toy this makes the "correct" target slightly worse-calibrated to the truth than the accidentally-well-calibrated Parkinson-fed HAR; a bias-corrected or component overnight+intraday HAR is the Phase-2 fix. (2) The return-fed models still score QLIKE against Parkinson though they too forecast close-to-close variance; scoring every model against the close-to-close proxy is the consistent end state, to be decided deliberately.

## D-015 · 2026-08-24 · Refit protocol = re-estimate every N, re-condition daily   [SETTLED]
Decision: "refit every N days" (D-014-planning: N=21) means parameters are re-estimated every N origins AND the model's conditional state is re-filtered on every origin's window in between (`recondition="daily"`, the default). ## D-014 · 2026-08-24 · QLIKE bias fix = parametric StudentT distribution   [SETTLED]
Decision: Student-t GARCH forecasts return a parametric `StudentT(loc, scale, df)` (closed-form mean/variance/CRPS) instead of a 199-point quantile grid; `forecast_moments` reads a distribution's own closed-form moments before falling back to a grid estimate.
Why: the grid spanned tau in [0.005, 0.995] with flat tails, and the evaluator's moments of that grid truncated the Student-t's tails — understating the variance ~24% at nu=3, so a *perfectly specified* forecast scored a QLIKE floor of 0.0407 instead of 0 (M1 report §4.2), growing exactly where the Student-t spec is meant to win. The parametric object removes the bias at its source with no RNG, so scoring stays bit-identical across runs. CRPS verified against numerical integration of two independent representations.
Alternatives rejected: tail-extrapolating the grid's moments (a patch on a lossy representation); sample-based Student-t (needs an RNG, breaks determinism).
Revisit-if: n/a — closed at the root.
